功能安全 Functional Safety

主线：失效 → 危害 → 风险 → 安全机制 ｜ 标准：ISO 26262（道路车辆功能安全）；延伸：ISO 21448 SOTIF

1. 什么是功能安全

功能安全关注电子电气系统（E/E）自身失效带来的不合理风险——即"系统没坏在黑客手里，而是自己 design/制造/运行出错，导致伤人"。注意它和"信息安全"是两套标准：

维度功能安全 (ISO 26262)信息安全 (ISO/SAE 21434)
关注风险来源随机硬件失效 + 系统性失效人为蓄意攻击（黑客、篡改、窃取）
目标把残留风险降到可接受水平保护资产机密性/完整性/可用性
典型手法HARA、ASIL、安全机制、FTA/FMEATARA、SecOC、HSM、加密
一句话记忆：功能安全管"系统自身失效"，信息安全管"他人蓄意攻击"。两者在车上要协同（security breach 也会引发 safety 事故）。

2. 核心概念：HARA → ASIL → 安全目标

概念阶段（Concept Phase）的串法：

  1. item 定义：先框定要分析的功能/系统边界（例如"自动紧急制动 AEB"）。
  2. HARA（危害分析与风险评估）：枚举危害事件 → 对每个评估 S（严重度）、E（暴露概率）、C（可控性）三个等级。
  3. ASIL 定级：由 S/E/C 组合得出 ASIL A~D（D 最严），QM 表示"质量管控即可、无需功能安全措施"。
  4. 安全目标（Safety Goal） + ASIL：针对每条危害给出定性的安全目标（如"避免非预期制动"）。
  5. 功能安全需求（FSR）→ 技术安全需求（TSR）→ 软硬件安全需求：逐级分解、可验证。
易错点：ASIL 不是给"零件"定的，是给"某条危害对应的安全目标"定的。同一个 ECU 里不同功能可能带不同 ASIL（混合关键度），要靠隔离机制处理。

2.1 ASIL 分解（ASIL Decomposition）

当某条安全目标定到 ASIL D（最严）时，可用冗余把要求"降档"：把一项高 ASIL 功能拆成两条相互独立、共同达成同一安全目标的低 ASIL 路径（如 ASIL D = ASIL B + ASIL B），前提是两条路径满足独立性 / 免干扰（Freedom from Interference）。本质是"用硬件或架构冗余换开发成本"——必须证明两条路径不会因同一根因同时失效，否则分解无效。

3. 开发流程：V 模型

ISO 26262 沿 V 模型展开，左边分解需求、右边逐级验证：

左侧（分解）右侧（验证）
概念 → 系统级 FSR系统集成测试（确认安全目标达成）
系统 → 硬件/软件 TSR硬件集成测试 / 软件单元测试
软件 → 软件安全需求软件/硬件架构度量评估

硬件要算随机硬件失效度量：SPFM（单点故障度量）、LFM（潜在故障度量）、PMHF（随机硬件失效概率度量，单位 FIT）。软件强调防御式编程与故障容错。

4. 安全分析手法：FMEA / FTA

  • FMEA（失效模式与影响分析）：自下而上，列每个部件"怎么失效、影响啥、严不严重（S/O/D 评分）"，偏设计早期筛查。
  • FTA（故障树分析）：自上而下，从顶层危害事件出发，用"与/或门"追根到基本事件，算顶事件概率，偏定量。
  • FMECA = FMEA + 危害性排序（Criticality）。

5. 软件安全机制：fail-safe 思维

功能安全对代码的硬要求是可预测地进入安全状态。两个可背的代码范式：

极简状态机（未知事件一律进安全态）：

enum class State { OFF, STANDBY, ACTIVE, FAULT };
enum class Event { POWER_ON, ACTIVATE, FAULT_OCCUR, RESET };

State transition(State s, Event e) {
    switch (s) {
        case State::OFF:     return e == Event::POWER_ON    ? State::STANDBY : State::OFF;
        case State::STANDBY: return e == Event::ACTIVATE    ? State::ACTIVE  : State::STANDBY;
        case State::ACTIVE:  return e == Event::FAULT_OCCUR ? State::FAULT   : State::ACTIVE;
        case State::FAULT:   return e == Event::RESET       ? State::OFF     : State::FAULT;
    }
    return State::FAULT;   // 兜底：任何未知组合都进安全状态
}

CRC-8（车规 E2E 信号保护，AUTOSAR E2E Profile 用 CRC+计数器+Data ID 防丢帧/乱序/重复）：

def crc8(data: bytes, poly: int = 0x07, init: int = 0x00) -> int:
    """CRC-8 逐位计算；poly=0x07 是常用 CRC-8/SMBUS 多项式"""
    crc = init
    for byte in data:
        crc ^= byte
        for _ in range(8):
            if crc & 0x80:
                crc = ((crc << 1) ^ poly) & 0xFF
            else:
                crc = (crc << 1) & 0xFF
    return crc

assert crc8(b"123456789") == 0xF4   # CRC-8/SMBUS 标准校验值

6. 深度学习与安全关键系统（重点交叉区）

本节将"算法/感知"经验与功能安全语言对接：当安全相关功能依赖深度学习模型时，感知算法的可靠性本身就是功能安全（尤其是 ISO 21448 SOTIF）的关注对象。

6.1 感知安全：SOTIF 的主战场

当安全相关功能依赖深度学习模型（检测、分割、深度估计）时，模型输出错误可能直接造成危害，这类风险不属于 ISO 26262 的"随机/系统性失效"，而属于 ISO 21448 SOTIF（预期功能安全）：关注"功能在性能不足或可预见误用下的风险"。

实例：激光雷达脏污检测与 SOTIF 的关联。以激光雷达脏污检测为例：传感器表面脏污会使点云出现残差异常，进而引入误检/漏检风险。采用"按仰角带动态阈值 + 干净帧基线扣除"的降误报思路，其目标与 SOTIF 关注的"功能在性能不足或可预见误用下的风险"一致——脏污检测本身即是一项感知安全相关功能。将感知/算法项目用功能安全语言重新表述，有助于厘清深度学习经验与安全标准的对应关系。

6.2 DL 模型的风险点与验证

风险表现验证/缓解手段
对抗样本微小扰动使模型误判对抗训练、红蓝对抗（FGSM/PGD 测试）、输入异常检测
分布偏移 / OOD真实场景与训练集不同OOD 检测、不确定性估计、长尾/corner case 覆盖
可解释性差出错难归因失败模式分析、影子模式（shadow mode）灰度
数据偏差特定群体/场景性能差场景仿真回放、覆盖度指标

6.3 AI Safety 与负责任部署

把模型放进安全相关链路前，至少要回答：最坏情况是什么、是否有 fail-safe 兜底、能否在仿真里大量回放验证、误报/漏报的代价是否可接受。这与功能安全"需求先行、边界优先"的思维方式完全一致。

6.4 SOTIF 场景分类：已知/未知 × 安全/不安全

SOTIF 将功能运行场景按"是否已知"与"是否安全"分为四类，用于指导验证资源的投放：

已知 Known未知 Unknown
安全 SafeArea 1：已知安全场景，常规运行Area 3：未知但安全，靠 ODD 边界与运行监控兜底
不安全 UnsafeArea 2：已知不安全（已知 corner case、已知误用），重点做针对性缓解与验证Area 4：未知不安全（未知失效模式），最难，靠充分测试、仿真回放、运行监控与 OTA 持续迭代
与前文实例呼应：激光雷达脏污导致的误检/漏检可归入"已知不安全（Area 2）"——其触发条件（脏污）与失效模式已知，因此可通过"仰角带动态阈值 + 干净帧基线扣除"等监测与缓解手段系统性地覆盖，而非依赖偶然发现。
关联阅读：系统安全页的"对抗样本"一节从攻击/信息安全视角讲同一件事——同一个对抗补丁，在功能安全里是"性能不足导致危害"，在信息安全里是"蓄意攻击导致危害"。两页对照看，能讲清 safety 与 security 的协同。
